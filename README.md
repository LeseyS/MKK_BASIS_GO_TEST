# Сервис управления задачами

Тестовое задание для МКК «Базис».

**Стек:** Go 1.25 · MySQL 8 · Redis · Docker Compose · chi · zerolog · Prometheus

---

## Быстрый старт

```bash
docker compose up --build
```

Поднимаются MySQL, Redis, одноразовый контейнер с миграциями и само приложение. Сервис слушает `http://localhost:8080`, Redis Commander — `http://localhost:8081`.

Проверить, что всё живо:

```bash
curl -s localhost:8080/ready -o /dev/null -w "%{http_code}\n"
```

### Смоук-сценарий

```bash
curl -s -X POST localhost:8080/api/v1/register \
  -d '{"name":"alice","email":"alice@example.com","password":"password123"}'

TOKEN=$(curl -s -X POST localhost:8080/api/v1/login \
  -d '{"email":"alice@example.com","password":"password123"}' | jq -r .token)

curl -s -X POST localhost:8080/api/v1/teams \
  -H "Authorization: Bearer $TOKEN" -d '{"name":"Alpha"}'

curl -s -X POST localhost:8080/api/v1/tasks \
  -H "Authorization: Bearer $TOKEN" -d '{"team_id":1,"title":"первая задача"}'
```

## Локальный запуск

Нужны поднятые MySQL и Redis (можно из compose: `docker compose up mysql redis migrate`).

```bash
cp .env.example .env
make migrate-install
make migrate-up
make run
```

Конфигурация читается из переменных окружения; `.env` подхватывается, если существует, но не обязателен — в контейнере переменные приходят напрямую из `docker-compose.yml`.

## API

Базовый префикс — `/api/v1`. Все эндпоинты, кроме регистрации и логина, требуют заголовок `Authorization: Bearer <token>`.

### Аутентификация

| Метод | Путь | Описание |
|---|---|---|
| `POST` | `/register` | регистрация, возвращает `id` |
| `POST` | `/login` | аутентификация, возвращает JWT |

### Команды

| Метод | Путь | Описание |
|---|---|---|
| `POST` | `/teams` | создать команду, создатель становится `owner` |
| `GET` | `/teams` | команды, в которых состоит пользователь |
| `POST` | `/teams/{id}/invite` | пригласить по email (только `owner`/`admin`) |
| `GET` | `/teams/stats` | статистика по командам |
| `GET` | `/teams/top-creators` | топ-3 создателя задач в каждой команде |

### Задачи

| Метод | Путь | Описание |
|---|---|---|
| `POST` | `/tasks` | создать задачу (только член команды) |
| `GET` | `/tasks` | список с фильтрами и пагинацией |
| `PUT` | `/tasks/{id}` | частичное обновление |
| `GET` | `/tasks/{id}/history` | история изменений |
| `GET` | `/tasks/invalid-assignees` | проверка целостности |

`GET /tasks` принимает `team_id` (обязательный), `status`, `assignee_id`, `limit` (по умолчанию 20, максимум 100), `offset`:

```
GET /api/v1/tasks?team_id=1&status=todo&assignee_id=5&limit=20&offset=0
```

```json
{
  "tasks": [ { "id": 1, "team_id": 1, "title": "…", "status": "todo", "assignee_id": null } ],
  "total": 1,
  "limit": 20,
  "offset": 0
}
```

`PUT /tasks/{id}` обновляет только переданные поля; каждое изменение пишется отдельной строкой в аудит:

```json
{ "status": "done", "title": "новый заголовок" }
```

### Коды ответов

| Код | Когда |
|---|---|
| `400` | невалидное тело или параметры |
| `401` | нет токена, токен истёк или подделан |
| `403` | пользователь не состоит в команде либо не хватает роли |
| `404` | объект не найден |
| `409` | email занят, пользователь уже в команде |
| `422` | исполнитель не является членом команды задачи |
| `429` | превышен лимит запросов |

Ошибки приходят единым форматом:

```json
{ "error": "you are not a member of this team: forbidden: insufficient role" }
```

### Служебные

`GET /live`, `GET /ready` — пробы. `GET /metrics` — метрики Prometheus.

## Схема данных

Шесть таблиц, десять внешних ключей: `users`, `teams`, `team_members` (many-to-many с ролью), `tasks`, `task_history`, `task_comments`.

Миграции лежат в `migration/mysql`, накатываются `golang-migrate` — тем же инструментом в compose, в `make migrate-up` и в интеграционных тестах.

### Индексы

| Индекс | Под какой запрос |
|---|---|
| `uq_users_email` | логин, приглашение по email |
| `idx_team_members_user` | список команд пользователя |
| `idx_tasks_team_status_created` | список задач с фильтром по статусу |
| `idx_tasks_team_status_updated` | статистика закрытых задач за 7 дней |
| `idx_tasks_assignee` | фильтр по исполнителю |
| `idx_tasks_created_at` | топ создателей за месяц |
| `idx_task_history_task_time` | история задачи |

## Сложные SQL-запросы

Три обязательных запроса из ТЗ вынесены в отдельные эндпоинты. Все ограничены командами вызывающего пользователя — иначе любой аутентифицированный видел бы чужую статистику.

**JOIN трёх таблиц с агрегацией** — `GET /teams/stats` ([исходник](internal/adapter/mysql/team_stats.go))

Название команды, число участников и количество задач, закрытых за последние 7 дней. `COUNT(DISTINCT …)` по обеим ветвям обязателен: без него соединение участников с задачами даёт декартово произведение. Условие по дате внесено в `CASE`, а не в `WHERE`, чтобы команды без свежих задач не выпадали из выдачи, а показывали ноль.

**Оконная функция** — `GET /teams/top-creators` ([исходник](internal/adapter/mysql/team_top_creators.go))

Топ-3 создателя задач в каждой команде за месяц через `ROW_NUMBER() OVER (PARTITION BY team_id ORDER BY tasks_created DESC)`. Именно `ROW_NUMBER`, а не `RANK`: при равном количестве задач `RANK` вернул бы больше трёх строк на команду.

**Подзапрос по связанным таблицам** — `GET /tasks/invalid-assignees` ([исходник](internal/adapter/mysql/tasks_invalid_assignee.go))

Задачи, исполнитель которых не состоит в команде задачи. `NOT EXISTS` попадает ровно в первичный ключ `team_members`.

## Оптимизация

**Кеш.** Список задач команды кешируется в Redis на 5 минут. Ключ включает все параметры фильтрации и пагинации, поэтому разные выборки не смешиваются. Любое создание или изменение задачи сбрасывает все ключи команды — уже после коммита транзакции, иначе параллельное чтение успело бы записать в кеш неактуальные данные. Недоступность Redis не ломает выдачу: ошибка логируется, ответ идёт из MySQL.

**Пагинация** выполняется на уровне БД через `LIMIT`/`OFFSET`, `total` считается отдельным запросом.

**Rate limiting.** Для авторизованных эндпоинтов ключом служит идентификатор пользователя из JWT, для регистрации и логина — IP (пользователя ещё нет). Лимит настраивается через `HTTP_RATE_LIMIT_PER_MINUTE`.

**Circuit breaker.** Обращения к почтовому сервису (мок) обёрнуты в `gobreaker`. Отказ отправки не роняет приглашение: участник уже добавлен в команду, ответ содержит `"email_sent": false`.

**Graceful shutdown.** По `SIGINT`/`SIGTERM` сервер перестаёт принимать соединения, дожидается активных запросов, затем закрываются Redis и пул MySQL.

**Метрики.** `http_server_requests_total` (метки: маршрут, статус) и `http_server_request_duration_seconds`. Метка маршрута берётся из шаблона chi (`/api/v1/tasks/{id}`), а не из URL, поэтому кардинальность ограничена числом эндпоинтов.

## Тесты

```bash
make test               # юнит-тесты с -race
make cover              # покрытие, отчёт в coverage.html
make integration-test   # интеграционные тесты на testcontainers
```

**Юнит-тесты** покрывают бизнес-логику через моки адаптеров. Покрытие критических методов:

| Пакет | Покрытие |
|---|---|
| `internal/usecase` | 97.8% |
| `internal/domain` | 100% |
| `pkg/jwtutil` | 100% |
| `pkg/passwordhash` | 91.7% |

**Интеграционные тесты** (`test/`, тег сборки `integration`) поднимают MySQL и Redis в testcontainers, накатывают миграции, запускают приложение и работают с ним по HTTP через клиент из [`pkg/task_client`](pkg/task_client). 48 проверок: аутентификация, ролевая модель, изоляция команд, фильтры и пагинация, аудит, кеширование, три аналитических запроса, rate limiting.

Клиент намеренно описывает структуры ответов сам, а не переиспользует `internal/dto`: так тесты проверяют реальный контракт API, и переименование поля в DTO ломает тест, а не проходит незамеченным.

Кеш проверяется записью мимо API — если выдача не замечает вставленную напрямую в БД строку, значит ответ пришёл из Redis.

## Структура

```
cmd/app             точка входа
config              сборка конфигурации из окружения
internal/
  controller/http   роутинг, HTTP-хендлеры, rate limiting
  usecase           бизнес-логика, интерфейсы адаптеров
  adapter/mysql     SQL-запросы
  adapter/redis     кеш
  domain            сущности и их валидация
  dto               объекты обмена между слоями
  middleware        аутентификация
  apperr            доменные ошибки
pkg/                инфраструктура: mysql, redis, jwt, логгер, метрики, HTTP-клиент
migration/mysql     миграции
test/               интеграционные тесты
```

Зависимости направлены внутрь: `usecase` объявляет интерфейсы, которые реализуют адаптеры, и ничего не знает о MySQL, Redis или HTTP. Ошибки транспортируются доменными сентинелами из `apperr` и разворачиваются в HTTP-коды только в слое контроллеров.
